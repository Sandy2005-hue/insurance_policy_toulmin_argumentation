# Health Insurance Claim Adjudication via Hybrid RAG & Toulmin Argumentation

A decision-support prototype that reads a free-text health insurance claim, retrieves the relevant clauses from a real policy wording, and writes a structured **Toulmin argument** ending in one of three verdicts: **Claim Approved**, **Claim Denied** or **Needs Human Review**. Every quote in the argument is checked against the retrieved policy text.

> **Educational project.** It is not legal or insurance advice and it is not a final adjudication. It uses one public policy wording and tests only on synthetic claims.

## Why this domain

In health insurance, a rejection has to be explainable and tied to the policy terms. That makes it a good fit for argumentation: the decision (claim), the facts (grounds), the rule applied (warrant), the policy text behind it (backing) and the exceptions (rebuttal) can each be stated and checked. A wrong approval or denial is costly, so the system escalates to a human when a fact the decision depends on is missing.

## How it works

```
User message
   |
   v
Router (app only): claim | policy question | off-topic (refused politely, no retrieval)
   |
   v
(claims) optional query rewriting: expand into formal policy keywords (Gemini)
   |
   v
Hybrid retrieval, run twice: coverage-oriented and exclusion/waiting-period-oriented
   BM25 (keyword) + ChromaDB / all-MiniLM-L6-v2 (dense) -> rank interleaving, deduplicated by clause ID, 4 clauses each
   |
   v
Adjudicator (Gemini, temperature 0): five-part Toulmin JSON, using only the retrieved clauses
   |
   v
Citation check: Backing and Rebuttal must appear word for word in the retrieved clauses
   |
   v
Streamlit UI: verdict, argument, retrieved clauses, citation-check result
```

**Toulmin mapping**

| Toulmin element | In this system |
|---|---|
| Grounds | Facts of the claim |
| Warrant | The policy rule applied |
| Backing | Verbatim policy quote supporting the rule |
| Rebuttal | Verbatim exclusion or waiting-period quote, or "No relevant exclusions found." |
| Claim | Verdict: Approved, Denied or Needs Human Review |
| Qualifier | Omitted by design. Uncertainty is expressed as *Needs Human Review* instead of hedging words |

**Citation check.** It verifies that quoted text exists in the retrieved clauses (and rejects empty, very short or spliced quotes). It does **not** prove that the quote is the most relevant one or that the verdict is correct.

## Tech stack

| Layer | Tools |
|---|---|
| Data preparation | Policy wording split into 157 clause-level chunks with IDs; section and clause titles are prepended before embedding |
| Embeddings and vector store | `all-MiniLM-L6-v2` (sentence-transformers), ChromaDB |
| Keyword retrieval | BM25 (`rank_bm25` via LangChain) |
| LLM | Google Gemini via `langchain-google-genai`, with an optional model fallback chain |
| Orchestration | LangChain |
| UI | Streamlit |

## Setup

Requires Python 3.10+ and a Google AI Studio API key.

```bash
git clone https://github.com/Sandy2005-hue/insurance_policy_toulmin_argumentation.git
cd insurance_policy_toulmin_argumentation
pip install -r requirements.txt
```

Create a `.env` file in the project root:

```
GOOGLE_API_KEY="your_api_key_here"
# optional
MODEL_CHAIN=gemini-3.8-flash,gemini-3.7-flash,gemini-3.6-flash
MODEL_COOLDOWN=300
```

Build the vector store (re-run whenever `data/policy_chunks.json` changes), then start the app:

```bash
python ingest.py
streamlit run app.py
```

## Evaluation

All numbers below come from synthetic questions and claims written from the policy text. Free-tier Gemini is rate limited, so the end-to-end benchmark pauses between calls and can be resumed.

```bash
python benchmark_retrieval.py                                   # no API calls
python compare_retrieval_strategies.py                          # no API calls
python benchmark_e2e.py --no-fallback --out e2e_with_rewriter.json
python benchmark_e2e.py --no-fallback --no-rewriter --out e2e_no_rewriter.json
python analyze_results.py e2e_with_rewriter.json
```

### 1. Retrieval on raw questions (25 questions, top 4 clauses)

| Configuration | Hit@4 | MRR |
|---|---|---|
| Dense only | 21/25 (84%) | 0.630 |
| BM25 only | 14/25 (56%) | 0.353 |
| Hybrid, rank interleaving (used by the app) | 18/25 (72%) | 0.443 |
| Hybrid, reciprocal rank fusion | 16/25 (64%) | 0.473 |
| Hybrid + hand-written expansions (upper bound, not a real system) | 25/25 (100%) | 0.980 |

Dense retrieval alone scored highest on raw questions. The 100% row only shows what is possible when the query already contains the clause's own vocabulary.

### 2. Retrieval on claims (25 claims; were the clauses that decide the claim retrieved?)

| Strategy | All deciding clauses | At least one |
|---|---|---|
| Current: 2 queries with fixed prefixes, hybrid interleaving | 14/25 | 20/25 |
| Same, dense only | 13/25 | 19/25 |
| Same, hybrid with reciprocal rank fusion | 16/25 | 21/25 |
| Plain claim, one query, 8 clauses | 14/25 | 17/25 |
| Plain claim + exclusion-focused query | 15/25 | 20/25 |

No strategy was clearly better. Differences are one to three claims out of 25. The clauses missed by every strategy are the same ones (mainly C.1, the inpatient benefit, and C.6, domiciliary treatment).

### 3. End-to-end verdicts (25 claims, exact match with the expected verdict)

| Metric | With query rewriting | Without query rewriting |
|---|---|---|
| Verdict accuracy | 18/25 (72%) | 16/25 (64%) |
| False approvals (expected Denied, predicted Approved) | 0/10 | 0/10 |
| Sent to human review | 14/25 | 16/25 |
| Citation check passed | 25/25 | 25/25 |
| All deciding clauses retrieved | 16/25 | 14/25 |
| Accuracy when all deciding clauses were retrieved | 16/16 | 13/14 |
| Accuracy when a deciding clause was missing | 2/9 | 3/11 |

Notes: runs used a model fallback chain, so different models answered different claims (with rewriting: gemini-3.8 on 8 claims, 3.7 on 11, 3.6 on 6; without: 3.8 on 18, 3.7 on 7). In the run with rewriting, one claim (GC-025) ran without rewriting because of a network error. Seven claims were wrong in both runs.

### Findings

- **Safety first.** No claim that should be denied was approved, and all claims that needed a human were escalated. Every error was an over-escalation to human review.
- **Retrieval is the bottleneck, not the reasoning.** When the deciding clauses were retrieved, the verdict was correct in 16 of 16 and 13 of 14 cases. When one was missing, it was correct in about a quarter of cases.
- **A vocabulary gap causes the misses.** Claims describe events ("fractured my ankle, admitted for 3 days") while clauses use abstract wording ("hospitalization due to disease/illness/Injury"), so keyword overlap is close to zero. Query rewriting helped a little; changing the query structure or the fusion method did not.
- **The citation check never failed.** It confirms that quotes are real, but it did not detect quotes that were irrelevant to the claim.

## Limitations

- **One policy.** Only the A PLUS Health Insurance wording, with its separate Policy Schedule unavailable. Plan-dependent values (for example waiting periods "as opted in the Schedule") cannot always be decided and should go to human review.
- **Conflicts in the wording.** Some clauses disagree (for example the maternity waiting period in D.2 versus G.4). The system is instructed to escalate such cases.
- **Synthetic test data.** The test claims are written by hand from the policy text that the system retrieves from. Results show how well the system follows this policy as written, not how it performs on real claims with bills, discharge summaries and doctors' notes.
- **Small test sets.** 25 claims and 25 questions; differences of one or two items are not meaningful. The same claims were used to diagnose errors, so a separate hold-out set is provided.
- **Mixed models and run-to-run variation.** Different Gemini models answered different claims, and outputs vary between runs even at temperature 0.
- **Over-escalation.** The system sends many answerable claims to human review (9 of 25 in the run without rewriting).
- **No partial approvals.** Co-payments, deductibles and sub-limits are not calculated.
- **Citation check scope.** It verifies quotes, not relevance or the verdict's correctness.
- **Input routing is an LLM call and can misclassify.** It is used in the app only, not in the benchmarks, and is not a security boundary.

## Future work

A query rewriter that names the policy concepts a claim relates to; splitting very long clauses (such as C.1) and enriching very short ones; a reranker; multi-policy support with a policy identifier on each clause; a structured intake form.

## Data and ethics

The policy wording is a public document. All test claims are synthetic, and no personal or patient data is used. The system is intended to assist a human reviewer, who makes the final decision.
